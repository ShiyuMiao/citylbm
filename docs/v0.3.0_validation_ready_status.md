# CityLBM v0.3.0 validation-ready status

This document is the short status index for the v0.3.0 validation branch. It is
intended for release notes, lab handoff and thesis/paper evidence tracking. It
does not report new CFD accuracy results.

## What v0.3.0 fixes

- Version metadata is standardized to `0.3.0`.
- `CustomTable` inflow supports `z(m), U(m/s), k(m2/s2)` instead of using
  `Uref` as a substitute for the AF table.
- The generated FluidX3D case records `profile_z_m[]`, `profile_u_lbm[]`,
  `profile_k_m2s2[]`, `profile_k_lbm[]`, `profile_origin_z_m`, SI/LBM scaling
  and CustomTable hash metadata.
- Partial `k` columns and duplicate profile heights are blocked before
  turbulent-inlet generation.
- The VTK/probe post-processing chain records source VTK steps, hashes,
  averaging-window evidence, probe distances, official coordinate deltas,
  compared component, normalization and U/k metrics.
- Native FluidX3D, CityLBM parity, inlet, boundary, roughness, time-averaging,
  grid-sensitivity and systematic-bias gates are separated so one good-looking
  plot or one R2 value cannot promote a diagnostic run.

## What runs immediately after installation

After installing `CityLBM.gha`, a user can open Grasshopper, place CityLBM
components, build a Rhino/GH case, generate FluidX3D source files and inspect
metadata with `Run Simulation / Mode 0 = Generate Case`.

This does not require launching FluidX3D. It is sufficient for checking GH
wiring, scene scale, CustomTable parsing and generated case files.

## What still requires a local FluidX3D path

Any real CFD solve still requires the user to set `Run Simulation / FluidX3D
Path` to an explicit local FluidX3D source or build root. For validation, the
path must be auditable and should contain a build file plus `src/setup.cpp`,
`src/defines.hpp`, `src/lbm.hpp` and `src/lbm.cpp`.

Auto-detected paths, copied executables and old VTK folders are not acceptable
evidence for Case A/E accuracy claims.

## Current scientific boundary

CityLBM v0.3.0 uses the AF `k` column to build a traceable diagnostic STG-lite
inlet when requested. This improves the software data path relative to v0.2.0,
but the current generated inlet is still a macroscopic velocity-field refresh.
It is not yet a paper-grade distribution-consistent DFM/SEM/precursor or
recycling inlet.

The source audit must therefore classify the current STG-lite route as:

- `inlet_source_method_class=stg_lite_correlated_velocity_field_only`
- `inlet_source_distribution_consistent=false`
- `paper_grade_inlet_source_gate=fail`

That failure is intentional. It prevents a diagnostic turbulent inlet from being
reported as SCI-level turbulent-inflow evidence.

## Required order before Case E paper claims

1. Run strict native FluidX3D Case A with official AF/RS inputs, explicit source
   evidence, complete final-window VTK output and no stale artifacts.
2. Pass inlet U/k preservation, inlet correlation, source-inlet, boundary,
   roughness, time-averaging, coordinate, component/Uref, LBM stability and grid
   sensitivity gates.
3. Run the matching CityLBM Case A workflow and pass native-vs-CityLBM parity
   plus additional-error gates.
4. Only after Case A closes, run Case E `ac + N` with the same evidence chain,
   `WP=3 CustomTable`, `Wind Direction=(0,-1,0)`, geometry scale `250`,
   official `AF_caseE.csv` and the 80 official `RS_caseE.csv` probes at
   `z=2 m`.

## Claim wording allowed now

Acceptable:

> CityLBM v0.3.0 is validation-ready: it fixes the AF U/k data path, records
> source and post-processing evidence, and blocks non-paper-grade inlet,
> boundary, time-averaging and parity conditions before accuracy claims.

Not acceptable yet:

> CityLBM v0.3.0 has completed SCI-level AIJ Case E validation.

Not acceptable yet:

> CityLBM v0.3.0 fully inherits native FluidX3D accuracy.

Those claims require new Case A and Case E solver runs with passing validation
gate reports.
